## 基础知识

### 信号量原语

信号量是 Dijkstra 提出的同步原语，本质上是一个非负整数 + 两个原子操作：

- **P 操作（wait/proberen）**：申请一个资源。计数 > 0 时减 1 立即返回；计数 = 0 时阻塞，等到 V 操作唤醒后重试
- **V 操作（signal/verhogen）**：释放一个资源。计数 + 1，如果有等待者则唤醒一个

信号量的初值决定用途：

| 初值 | 用途 | 典型场景 |
|------|------|----------|
| 1 | 互斥锁（mutex） | 同一时刻只允许一个进程访问临界区 |
| 0 | 同步等待（事件） | 一个进程等另一个进程完成某事 |
| N | 资源池 | 限制同时访问某资源的进程数 |

本 lab 的验收程序用初值 0：子进程 `sem_p` 后阻塞，等父进程 `sem_v` 唤醒。

### xv6 的 sleep / wakeup

xv6 提供两个内核函数让进程阻塞和唤醒：

```c
void sleep(void *chan, struct spinlock *lk);
void wakeup(void *chan);
```

`chan` 是等待信道（waiting channel），是一个任意的地址。约定：

- 多个进程可以睡在同一个 chan 上
- `wakeup(chan)` 唤醒所有睡在该 chan 上的进程（让它们重新进入 RUNNABLE）
- chan 必须是稳定地址（不能是栈上的局部变量），通常用某个全局变量的地址

### `sleep` 的源码（`kernel/proc.c` 约 640 行）

```c
void
sleep(void *chan, struct spinlock *lk)
{
  struct proc *p = myproc();

  if(lk != &p->lock){
    acquire(&p->lock);
    release(lk);
  }

  p->chan = chan;
  p->state = SLEEPING;

  sched();

  p->chan = 0;

  if(lk != &p->lock){
    release(&p->lock);
    acquire(lk);
  }
}
```

关键点：调用 `sleep` 前必须持有 `lk`，`sleep` 内部会原子地释放 `lk` 并设置 SLEEPING 状态、调 `sched` 切走；醒来后重新获取 `lk`。这个"原子释放 + 睡眠"是避免丢失唤醒的核心。

### `wakeup` 的源码（`kernel/proc.c` 约 674 行）

```c
void
wakeup(void *chan)
{
  struct proc *p;

  for(p = proc; p < &proc[NPROC]; p++) {
    acquire(&p->lock);
    if(p->state == SLEEPING && p->chan == chan) {
      p->state = RUNNABLE;
    }
    release(&p->lock);
  }
}
```

`wakeup` 扫描整个进程表，把所有睡在 `chan` 上的 SLEEPING 进程改成 RUNNABLE。注意它持 `p->lock`，这正是 `sleep` 也持 `p->lock` 的原因——同一把锁保证了"检查 p->chan + 改 p->state"和"设置 p->chan + 设置 SLEEPING"不会交错。

### 丢失唤醒问题

如果 P 操作不使用 sleep/wakeup，而是简单地：

```c
// 错误示范
while(semtab[sem].count <= 0)
    ;  /* 忙等，CPU 浪费 */
semtab[sem].count--;
```

这是忙等，浪费 CPU。如果加 sleep 但锁使用不当：

```c
// 错误示范
if(semtab[sem].count <= 0)
    sleep(&semtab[sem], 0);  /* 没持锁 */
```

可能发生"丢失唤醒"：

```text
进程 A：检查 count = 0，准备 sleep
进程 B：V 操作，count++，wakeup（A 还没睡着，wakeup 无效）
进程 A：进入 sleep，永远等不到下一次 wakeup
```

xv6 的 `sleep` 强制要求传 spinlock，并通过"原子释放 lk + 进入 SLEEPING"消除这一窗口。CP② 的实现必须正确使用这个机制。

### P/V 操作的 xv6 实现模板

P 操作的标准写法：

```c
acquire(&semlock);
while(semtab[sem].count <= 0)
    sleep(&semtab[sem], &semlock);   // 原子释放 semlock 进入睡眠
semtab[sem].count--;
release(&semlock);
```

V 操作的标准写法：

```c
acquire(&semlock);
semtab[sem].count++;
wakeup(&semtab[sem]);                 // 唤醒等在该信号量上的所有进程
release(&semlock);
```

注意几个关键点：

- P 用 `while` 而非 `if`：防止虚假唤醒（多个等待者被同时唤醒，但只有一个能拿到资源）
- chan 用 `&semtab[sem]` 而非 `sem`（必须是稳定地址，不能是局部变量或纯整数）
- V 操作 `count++` 必须在 `wakeup` 之前，保证被唤醒的进程重检时能看到新计数

### 信号量池定义（`kernel/sysproc.c` 约 158-166 行）

```c
struct sem {
  int count;          // 信号量计数（P 减 V 增）
  int initialized;    // 是否已初始化
};
static struct sem semtab[10] __attribute__((unused));   // 10 个信号量槽
static struct spinlock semlock __attribute__((unused)); // 保护 semtab
static int semlock_inited __attribute__((unused)) = 0;
```

简化设计：

- 全局最多 10 个信号量，sem id 是 `semtab[]` 的下标
- 一个 spinlock `semlock` 保护整个 semtab
- `semlock_inited` 标记是否已初始化（懒初始化）

`__attribute__((unused))` 是因为骨架阶段这些变量还没被使用，加这个属性避免编译告警；CP 实现后这些变量会被读写，属性可以去掉，但留着也不影响。

### 三个 CP 在调用链中的位置

```text
ipctest 调用流程：
  sem_init(0, 0)  ─→ sys_sem_init CP① ─→ semtab[0].count = 0; initialized = 1
  fork
  │
  ├─ 子进程 sem_p(0) ─→ sys_sem_p CP② ─→ while(count<=0) sleep; count--
  │                                    （阻塞）
  └─ 父进程 sleep(3)
            ↓ 3 秒后
            sem_v(0) ─→ sys_sem_v CP③ ─→ count++; wakeup(&semtab[0])
            ↓
            子进程被唤醒，重检 count，P 操作成功
            ↓
            wait(0) 收回子进程
```

三个 CP 必须配套：缺 CP① 时 `semtab` 没初始化；缺 CP② 时子进程不阻塞；缺 CP③ 时唤醒永不发生。

### 任务2：CP① 实现 `sys_sem_init`

#### 步骤1：阅读信号量池定义（约 158-166 行）

源码见"代码导读"。`semtab[10]` 是全局信号量池，每个 `struct sem` 有 `count` 和 `initialized` 两个字段。`semlock` 保护整个池的并发访问。

#### 步骤2：理解 `sem_init` 的语义

`sem_init(sem, value)` 把第 `sem` 号信号量的 `count` 设为 `value`，`initialized` 设为 1。需要做：

- 用 `argint(0, &sem)` 取 sem id
- 用 `argint(1, &value)` 取 value
- 检查 `sem` 在 `[0, 10)` 范围、`value >= 0`
- 懒初始化 semlock（`if(!semlock_inited) { initlock(&semlock, "semtab"); semlock_inited = 1; }`）
- 持 `semlock` 修改 semtab[sem] 的 count 和 initialized

#### 步骤3：实现 `sys_sem_init`

`sys_sem_init`（约 193 行）当前是占位 `return -1;`。按上述思路补全。修改共享状态时必须持 `semlock`，避免与其他 CPU 上的进程竞争。

### 任务3：CP② 实现 `sys_sem_p`

#### 步骤1：阅读 `sleep`（约 640 行）

源码见"基础知识"。`sleep(chan, lk)` 在调用前必须持 `lk`，进入睡眠会原子释放 `lk`，醒来后重新获取。

#### 步骤2：理解 P 操作的完整流程

`sys_sem_p(sem)` 实现模板：

1. `argint(0, &sem)` 取 sem id
2. 校验 `sem` 范围、`initialized == 1`
3. `acquire(&semlock)`
4. `while(semtab[sem].count <= 0)`
   - `sleep(&semtab[sem], &semlock)` —— 原子释放 semlock 进入睡眠，醒来重新获取
5. `semtab[sem].count--`
6. `release(&semlock)`
7. 返回 0

注意几个关键点：

- 用 `while` 而不是 `if`：多个进程可能同时被 `wakeup` 唤醒，但只有一个能拿到资源，其他重检后继续睡
- chan 用 `&semtab[sem]`（稳定地址，每个 sem id 一个独立信道）
- 不能在持 semlock 时 return -1，必须先 release

#### 步骤3：实现 `sys_sem_p`

`sys_sem_p`（约 227 行）当前是占位 `return -1;`。按上述模板实现。

#### 步骤4：构建运行

```bash

```

```text

（3 秒过去）
parent: calling sem_v to wake child
sem_v failed (CP③ not done?)
```

子进程**应该已经阻塞**在 `sem_p`（这是 CP② 生效的证据，子进程不再立即返回 -1）。但 CP③ 还没实现，父进程 sem_v 失败，子进程一直阻塞。继续 CP③。

### 任务4：CP③ 实现 `sys_sem_v`

#### 步骤1：阅读 `wakeup`（约 674 行）

源码见"基础知识"。`wakeup(chan)` 扫描进程表，把所有睡在 chan 上的 SLEEPING 进程改成 RUNNABLE。

#### 步骤2：理解 V 操作的完整流程

## 常见问题（FAQ）

| 现象 | 原因 / 解决 |
|------|------------|
| `ipctest` 输出 `sem_init failed` | CP① 没实现，或 `argint` 失败 |
| 子进程不阻塞，直接打印 `got sem` | CP② 没判断 count <= 0；或 semtab[0].count 初值不是 0 |
| 子进程阻塞后父进程 sem_v，子进程不醒 | chan 不一致（P 和 V 必须用同一个 `&semtab[sem]`） |
| 系统卡死 | 持 semlock 时调 wakeup 但没 release；或循环条件死循环 |
| `count` 出现负值 | P 操作没用 `while` 重检，多个等待者同时通过 if |
| `make build` 报 unused variable | 骨架的 `__attribute__((unused))` 在 CP 实现后可以去掉，但留着也不影响 |
| 系统启动卡死 | 误改了 sleep / wakeup / scheduler 等基础设施。本 lab 只动 sysproc.c |
