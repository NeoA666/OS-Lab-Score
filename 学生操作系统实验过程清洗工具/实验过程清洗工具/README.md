# 实验过程清洗工具

重放学生 `term/*.out.gz` 与可选的 `*.tim.gz` 终端录像，提取 Shell 命令、终端对话、完整转写、Claude 对话和按 Lab 分类的实验过程时间线。工具只读取录像和采集日志，不执行学生命令。

主要收益、适用场景和增量边界见 [主要改进说明](主要改进说明.md)；重放调度、缓存契约和验证细节见 [重构说明](REFACTORING.md)。

## 安装

需要 Python 3.9+。服务器只需 Python 和本目录已有 requirements，不需要额外的原生库：

```bash
python3 -m pip install -r requirements.txt
```

依赖为 `pyte>=0.8,<1` 和 `wcwidth>=0.2,<1`。`pyte` 是终端状态机，按 LGPL-3.0-or-later 发布；本工具通过公开 Python API 使用它，许可证文本随依赖包提供。`python-isal` 和 `indexed_gzip` 不属于本工具的必需依赖。

## 运行模式与并行度

默认是混合模式：每条录像只做一次精确终态转写和可审计索引；只有 Claude 双角色标记、解析/计时异常或显式指定的录像才逐时间帧重放。`exact` 模式对选中范围内全部录像逐帧重放，适合复核和回归基准。父进程负责排序和汇总，录像任务在 Windows `spawn` 上下文中使用 Python 多进程执行。

默认从仓库根的 `操作系统实验数据记录/` 读取，并写入同级的 `操作系统实验数据记录-已清洗/`。位置参数可指定其他输入根，`--output` 可指定输出根。

```bash
# 默认 hybrid；默认并行度为 min(12, 可用 CPU 核数)
python3 replay_term_qa.py

# 只处理匹配的学生，或只刷新时间线阶段
python3 replay_term_qa.py --student 2406080102
python3 replay_term_qa.py --timeline-only

# 全量逐帧复核；服务器也可显式固定 12 个进程
python3 replay_term_qa.py --replay-mode exact --workers 12

# 混合批次中重复指定需要逐帧复核的录像 ID
python3 replay_term_qa.py --replay-mode hybrid \
  --exact-recording 2306010113-刘梓宸-20260911-2046/term/20260910T102030-1234 \
  --exact-recording 20260910T104501-5678
```

`--workers` 接受正整数；正式输出按稳定顺序聚合，`1` 和 `12` worker 的 Markdown/JSON 内容一致。`--exact-recording` 使用输入根相对的 `<学生目录>/term/<录像ID>`；裸录像 ID 仅在当前选择范围唯一时可用。原有的 `--student`、`--force`、`--timeline-only` 和 `--no-timeline` 继续有效；`--timeline-only` 与 `--no-timeline` 不能同时使用。

## 缓存与失效

录像级缓存位于输出根的 `.replay-cache/`。缓存键由稳定的学生身份、录像名、`.out.gz`/`.tim.gz` 输入哈希和 timing 状态组成；条目保存相对来源路径、分析器签名、Lab 区间、提示符/命令锚点、时间索引和可选精确帧结果。分析器签名只覆盖录像分析规则、相关代码和 `pyte`/`wcwidth` 版本，因此报告文案调整不会让录像缓存失效。精确结果可以满足后续 hybrid 请求；因此切换模式不会重复计算已存在的能力。

缓存按能力复用：学生再次全量提交时，只要某一对录像内容未变，即使提交目录的采集时间变了也会直接复用；只修改一条 `.out.gz`、`.tim.gz`、分类规则或相关分析器时，仅重算受影响的录像。多个保留提交中的同一录像会合并为一个任务；其中任一处要求精确复核时，该任务直接升级为精确分析。`events.jsonl` 变化只重建日志佐证、相关时间线和学生汇总，不重放未变化录像。只有不带 `--student` 的完整源扫描会清理旧分析器版本以及不再属于当前源扫描的缓存条目；带 `--student` 的局部扫描不会清理其他学生的缓存。缓存清理不会删除原始数据、用户文件或正式报告。`--force` 仍会忽略命中并重建选中范围。

缓存断点是整条录像，不是录像内部的 timing 帧。采集器如果持续追加同一个 `.out.gz` / `.tim.gz`，这对文件会整条重放；将会话拆成独立录像后，之前的录像可完全跳过。扫描时会校验输入哈希与文件状态；文件在扫描、缓存查找或分析期间变化会形成结构化诊断，不会写入或复用不一致缓存。`.replay-cache/` 和 `.tim.gz` 的链接/junction 不会被跟随到外部位置。

## 已测性能

在同一输入规模下，旧串行全量记录为 `54 分 29 秒`；当前 `hybrid --workers 12` 使用新输出根完成 625 条录像分析和报告/时间线生成，墙钟时间为 `9 分 52 秒`，约为旧流程的 `18.10%`，即约 **5.53 倍**加速。两次运行均有 31 个输入学生目录，其中 29 名学生完成处理；另 2 个目录没有可处理录像，按工具约定返回部分失败。详细条件见 [重构说明](REFACTORING.md#冷缓存基准)。

## 证据等级与时间语义

- **E1 终端屏幕证据**：来自 pyte 终端状态的精确帧、录像字节范围或一次性终态转写；可回查录像相对位置。Claude QA、命令输出和完整转写都沿用同一录像级证据。
- **E2 采集日志佐证**：来自 `events.jsonl` 的采集事件，只用于补充发生关系。报告会显示日志行号、关联置信度和时间语义，明确标注“采集日志佐证”，不把日志内容当成终端屏幕证据。

计时文件缺失、损坏或未覆盖完整录像时保留无时间证据；相对时间和绝对时间字段写为未知或缺失，不伪造时间。单条录像失败会形成结构化诊断并保留其他录像和部分报告。

## 其他阶段

生成简洁时间线：

```bash
python3 generate_readable_timeline.py
```

每个学生至少需要一个常规 `term/*.out.gz`；缺少录像、损坏计时文件、符号链接或不安全目录会被独立报告，不生成伪造的空结果。
