# 终端重放主要改进说明

这次改造解决的问题是：学生再次提交完整目录时，旧流程会重复解压和重放大量未变化的终端录像。现在工具把分析粒度改为单条录像，正常情况下只分析新增或变化的录像，并由同一份分析结果同时生成报告和时间线。

## 结果

在实际数据集上，旧串行全量流程耗时 `54 分 29 秒`。新的默认运行方式 `hybrid --workers 12` 处理 625 条录像耗时 `9 分 52 秒`，约为旧流程的 `18.10%`，达到约 **5.53 倍**墙钟时间加速。

这里的 12 是最多启动 12 个独立 Python 进程，不是 12 个线程。终端状态机 `pyte` 的主要工作在 Python 代码中，多线程会受 GIL 限制；多进程才能同时利用多个 CPU 核心。默认值为 `min(12, 可用 CPU 核数)`。

## 主要改进

| 改进 | 原来的工作方式 | 现在的工作方式 | 直接收益 |
| --- | --- | --- | --- |
| 录像级缓存 | 学生目录变化后重复处理此前录像 | `.replay-cache/` 按学生身份、录像名、输入哈希和分析器签名复用结果 | 全量重新提交时跳过未变化录像 |
| 混合重放 | 每条录像都按 timing 帧构造 Screen 快照 | 所有录像只做一次终态转写和索引；仅 Claude 候选、解析/计时异常或指定录像逐帧扫描 | 大部分普通 Shell 录像不再承担逐帧成本 |
| 一次性终态转写 | 为大量 timing 块反复维护整屏状态 | 完整正文一次 `ByteStream.feed(body)` 完成终态、滚屏和清屏转写 | 减少 Python 对象创建和屏幕复制 |
| 分析结果复用 | 报告、Claude QA、时间线分别读取或重放同一录像 | 单条录像分析结果同时供报告和时间线消费 | 不再为不同产物重复解压与重放 |
| 多进程调度 | 单个进程按学生串行处理 | 父进程排序汇总，Windows `spawn` 子进程按录像并行分析 | 充分利用 CPU，并保持输出顺序稳定 |
| 日志独立失效 | 修改采集日志可能触发终端阶段重建 | `events.jsonl` 只重建 E2 日志佐证、时间线和学生汇总 | 日志更新不重放未变化录像 |

## 默认模式如何工作

默认的 `hybrid` 模式分两层处理：

1. 每条录像都会读取一次，生成完整终端终态转写、Lab 区间、命令锚点、字节范围和时间索引。
2. 只有出现 Claude 用户和回复标记、命令解析失败、timing 缺失/损坏/未覆盖正文，或通过 `--exact-recording` 指定的录像，才会按时间帧逐步扫描 Screen。

这意味着普通 Shell 录像仍然有可审计的终态和命令证据，但不为没有 Claude 对话且没有异常的录像保存大量逐帧状态。`exact` 模式仍可对选中范围的所有录像逐帧重放，用于复核或回归。

```bash
# 默认：hybrid + min(12, 可用 CPU 核数) 个进程
python3 replay_term_qa.py

# 对全部选中录像做逐帧复核
python3 replay_term_qa.py --replay-mode exact --workers 12

# 在混合批次中复核指定录像；参数可重复
python3 replay_term_qa.py --exact-recording 学生目录/term/录像ID
```

## 全量提交时会发生什么

学生新提交一个完整目录时，工具先对每条 `.out.gz` / `.tim.gz` 建立输入快照并比较哈希。

| 输入变化 | 终端录像是否重新分析 |
| --- | --- |
| 提交目录或采集时间改变，录像内容相同 | 否，直接复用录像缓存 |
| 只改变一条 `.out.gz` 或 `.tim.gz` | 只重新分析该条录像 |
| 只改变 `logs/events.jsonl` | 否，只刷新日志佐证、时间线和学生汇总 |
| 请求 `--exact-recording` 或 `--replay-mode exact` | 将需要的录像升级为逐帧分析 |
| 使用 `--force` | 忽略选中范围内的缓存并重新分析 |

当前断点位于**录像边界**。如果采集器持续向同一个 `.out.gz` / `.tim.gz` 追加内容，文件哈希会变化，该录像会从头重新分析。把会话拆成独立录像后，已经结束的录像可以完全跳过。这一边界避免了 gzip 内随机续读和终端 Screen 状态恢复带来的额外依赖与审计复杂度。

## 输出、证据和可靠性

正式输出仍保持原有的按人分类、按 Lab 分类、汇总报告和运行日志目录。缓存只放在输出根的 `.replay-cache/`，不会删除原始录像、用户文件或正式报告。

- **E1 终端屏幕证据**来自终端状态、命令锚点、字节范围和可用的精确帧。
- **E2 采集日志佐证**来自 `events.jsonl`，明确标出日志行号、关联置信度和日志自身的时间语义，不能代替 E1。
- timing 文件缺失、损坏或未覆盖完整录像时，工具保留无时间证据，而不会伪造相对时间或绝对时间。
- 单条录像失败只形成结构化诊断和部分失败报告，其他录像继续处理。

缓存会校验输入哈希、分析器签名、缓存能力和文件状态。精确结果可以被后续 hybrid 运行直接复用；分析器版本变更、录像内容变更或当前完整源扫描中已消失的录像缓存会被清理。

## 已验证的范围

回归测试覆盖一次性转写的清屏、滚屏和宽字符，复杂命令回显，Claude 帧提取，缺失或损坏 timing，跨 Lab 录像，无 Claude 标记时跳过逐帧 QA，缓存失效、`events.jsonl` 独立更新、不同 worker 数的正式输出哈希一致，以及 Windows `spawn` 调度。
