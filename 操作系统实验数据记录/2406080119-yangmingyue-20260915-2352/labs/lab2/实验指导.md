## 基础知识

### 进程与进程控制块

进程是操作系统对运行中程序的基本抽象。每个进程在 xv6 中由一个 `struct proc` 表示（定义在 `kernel/include/proc.h`），它保存了进程运行所需的全部信息。本 lab 关注其中四个字段：

| 字段 | 类型 | 含义 |
|------|------|------|
| `pid` | `int` | 进程 ID，全局唯一 |
| `parent` | `struct proc *` | 指向父进程控制块的指针 |
| `state` | `enum procstate` | 进程状态（UNUSED / SLEEPING / RUNNABLE / RUNNING / ZOMBIE） |
| `xstate` | `int` | 进程退出码，留给父进程 `wait` 读取 |

`myproc()` 是内核中获取当前进程控制块指针的常用接口，返回 `struct proc *`。

### 进程状态机

xv6 进程在五个状态间转换：

```text
                 fork / allocproc
                       │
                       ▼
                   RUNNABLE ◄──────────┐
                       │               │
                  scheduler 选中       │
                       │               │
                       ▼               │
                   RUNNING            │
                       │               │
            ┌──────────┼──────────┐    │
            │          │          │    │
          exit       yield/IO    时间片 │
            │          │          │    │
            │          └──────────┴────┘
            ▼
         ZOMBIE  ◄── exit 写入退出码和状态
            │
      parent wait/wait4
            │
            ▼
         UNUSED  ◄── freeproc 清空
```

- RUNNABLE：可运行，等待 CPU
- RUNNING：正在某个 CPU 上执行
- SLEEPING：阻塞等待事件（如等子进程退出、等 IO、等锁）
- ZOMBIE：已退出但尚未被父进程 `wait` 回收
- UNUSED：控制块空闲，可被 `allocproc` 重新分配

### 进程生命周期：fork / exec / wait / exit

xv6 进程从创建到消亡的标准路径：

1. **fork**：父进程调用，复制自身产生子进程。子进程的 `parent` 字段指向父进程。子进程的 `pid` 由 `allocproc` 分配。
2. **exec**（可选）：把当前进程的内存映像替换为某个新程序。`init` 启动 `sh` 用的就是 exec。
3. **exit**：进程主动结束，状态变为 ZOMBIE，退出码存入 `xstate`。
4. **wait**：父进程调用，扫描自己的 ZOMBIE 子进程，回收其资源，把 `xstate` 复制给用户态。

本 lab 的 `wait4` 是 `wait` 的"指定 pid"版本：父进程不再等任意子进程，而是等一个具体的 pid。Linux 的 `waitpid` 就是这种语义。

### 主动让出 CPU：协作式调度

xv6 默认是抢占式调度——时钟中断触发 `yield()`，强制当前进程让出 CPU。进程也可以**主动**让出，典型场景是用户态的 `sched_yield()` 调用。

`kernel/proc.c` 中已有现成的 `yield()` 函数：

```c
void yield(void) {
  struct proc *p = myproc();
  acquire(&p->lock);
  p->state = RUNNABLE;
  sched();
  release(&p->lock);
}
```

它做的事：把当前进程状态从 RUNNING 改为 RUNNABLE，调 `sched()` 切换到调度器上下文。下一次调度轮到本进程时，会从 `sched()` 返回处继续执行。

`sched_yield` 系统调用的内核实现可以复用这个现成机制，不必重写调度逻辑。

### 用户态指针与 `copyout2`

`wait4(pid, &status)` 中 `status` 是用户态变量的地址。内核里不能直接 `*status = ...`：

- 用户态指针指向的虚拟地址在内核页表里不一定有效
- 即使有效，也可能属于另一个进程的地址空间
- 用户可能传入非法地址，内核直接解引用会 panic

正确做法是用 `copyout2`：

```c
int copyout2(uint64 dstva, char *src, uint64 len);
```

本仓库为每个进程建立了包含用户区映射的内核页表，`copyout2` 会先检查目标范围是否落在当前进程的 `[0, sz)` 内，再通过当前页表下的地址执行复制。它不是完整的 PTE 权限验证器，但提供了本实验统一的用户地址写回边界。不要在 wait4 中绕过它自行处理 status。

```c
if(addr != 0 && copyout2(addr, (char *)&np->xstate, sizeof(np->xstate)) < 0) {
    return -1;
}
```

`wait4` 中的 `status` 处理方式与 `wait` 一致。

### 关键参考实现

#### `sys_getpid`（同文件顶部，约 69 行）

```c
uint64 sys_getpid(void) {
    return myproc()->pid;
}
```

`getppid` 的实现思路与 `getpid` 类似，但取的是父进程的 pid 字段。

#### `wait`（`kernel/proc.c` 约 476 行）

`wait4` 主要参考 `wait`。`wait` 的核心循环：

```c
for(;;) {
    havekids = 0;
    for(np = proc; np < &proc[NPROC]; np++) {
        if(np->parent == p) {                    // 是我的子进程
            acquire(&np->lock);
            havekids = 1;
            if(np->state == ZOMBIE) {            // 已退出
                pid = np->pid;
                if(addr != 0 && copyout2(addr, ...) < 0) {
                    release(...); return -1;
                }
                freeproc(np);
                release(...); return pid;
            }
            release(&np->lock);
        }
    }
    if(!havekids || p->killed) { release(&p->lock); return -1; }
    sleep(p, &p->lock);                           // 没子进程退出，睡眠等
}
```

`wait4` 相对 `wait` 多一个 pid 过滤条件：扫描时不仅检查"是不是我的子进程"，还要检查"pid 是不是等于参数指定的值"。

### 三个 CP 在 `sysproc.c` 末尾

```text
sysproc.c 末尾：
    sys_getppid      ← CP① 占位 return -1
    sys_sched_yield  ← CP② 占位 return -1
    sys_wait4        ← CP③ 占位 return -1
```

三个 CP 之间相对独立，但建议按顺序实现——`getppid` 最简单（理解 `struct proc` 字段），`sched_yield` 引入调度协作点，`wait4` 综合考查 `wait()` 机制和用户态指针。

### 任务2：CP① 实现 `sys_getppid`

#### 步骤1：阅读 `sysproc.c` 中的 `sys_getpid`（约 69 行）

```c
uint64 sys_getpid(void) {
    return myproc()->pid;
}
```

`myproc()` 返回当前进程的 `struct proc *`，`->pid` 取其 pid 字段。

#### 步骤2：阅读 `struct proc`（`kernel/include/proc.h`）

关注 `parent` 字段：

```c
struct proc *parent;         // Parent process
```

`parent` 是指向父进程控制块的指针，由 `fork` 在创建子进程时设置。

#### 步骤3：实现 `sys_getppid`

`sys_getppid`（约 182 行）当前是占位 `return -1;`。改成返回当前进程父进程的 pid。

实现思路：从 `myproc()` 出发，通过 `->parent` 找到父进程，再取 `->pid`。注意三步解引用的顺序。

实现完成后重新构建运行 `proctest`，期望 `ppid` 显示为非 -1 的合法值（通常是 `sh` 的 pid）。

### 任务3：CP② 实现 `sys_sched_yield`

#### 步骤1：阅读 `kernel/proc.c` 中的 `yield()`（约 604 行）

```c
void yield(void) {
    struct proc *p = myproc();
    acquire(&p->lock);
    p->state = RUNNABLE;
    sched();
    release(&p->lock);
}
```

`yield()` 把当前进程状态置为 RUNNABLE，调 `sched()` 切换到调度器，让其他 RUNNABLE 进程获得 CPU。本进程会在下次调度时从 `sched()` 返回处继续。

#### 步骤2：理解 `sched_yield` 的语义

用户态调用 `sched_yield()` 表示"我现在没什么事，先把 CPU 让出来"。返回 0 表示成功。返回后，当前进程仍能继续运行，只是让出了这一次时间片。

#### 步骤3：实现 `sys_sched_yield`

`sys_sched_yield`（约 213 行）当前是占位 `return -1;`。改造成调用现成的 `yield()`，并在返回 0 表示成功。

复用 `yield()` 即可，不要重写调度逻辑。

#### 步骤4：（可选）手动验证

写一个小用例循环调用 `sched_yield()`，确认进程不会异常退出。或者直接在 shell 中连续敲几个命令，观察系统是否仍正常调度。

### 任务4：CP③A / CP③B 实现简化 wait4

#### 步骤1：先定位状态写点

动笔前先在 `kernel/proc.c` 找出：

- 哪个函数把进程写成 `ZOMBIE`
- 哪个函数最后把它写回 `UNUSED`

本实验的关键事实是：`exit()` 负责提交退出码并进入 ZOMBIE；`wait/wait4` 只发现 ZOMBIE，`freeproc()` 才负责最终回收。

#### 步骤2：明确本实验的简化 ABI

`wait4(pid, &status)` 只实现两种 pid 语义：

- `pid > 0`：等指定 pid 的子进程
- `pid == -1`：等任意子进程

`pid == 0` 和进程组语义、Linux wait4 的 `options/rusage` 参数不在本实验范围内。

#### 步骤3：CP③A 参数包装（`kernel/sysproc.c`）

这一层只负责：

1. 用 `argint(0, &pid)` 取 pid
2. 用 `argaddr(1, &status_addr)` 取用户 status 地址
3. 校验简化 pid 语义
4. 调用 `kernel/proc.c` 的 `wait4(pid, status_addr)`

不要在 sysproc.c 中复制进程表扫描循环。

#### 步骤4：CP③B 进程机制（`kernel/proc.c`）

参考现有 `wait()`，实现：

1. 持父进程锁扫描进程表，只匹配自己的子进程和目标 pid
2. 匹配子进程是 ZOMBIE 时，先用 `copyout2` 写回 `xstate`
3. 写回成功后才调用 `freeproc()` 回收并返回 pid
4. 匹配子进程存在但尚未退出时，`sleep(p, &p->lock)` 等待并在醒来后重新扫描
5. 没有匹配子进程或调用者被 kill 时才返回 -1

注意：`copyout2` 失败时不能先回收；ZOMBIE 必须保留，调用者才能用合法地址或空 status 重试。

#### 步骤5：构建运行

```bash

make fs   # proctest 是用户程序，修改后必须重新打包
make run
```

在 shell 中执行 `proctest`。它会分别检查：

- 子进程看到的 ppid 是否等于父进程 pid
- `sched_yield()` 是否成功返回 0
- `wait4(pid, &status)` 是否返回目标 pid 和退出码 42


### 现象分层定位

| 故障层 | 现象 | 排查方向 |
|--------|------|----------|
| `getppid` 错 | `proctest` 第一行 `ppid = -1` 或乱值 | CP①：是否取到 `myproc()->parent->pid`？ |
| `sched_yield` 错 | 调用后系统卡住或 panic | CP②：是否调用 `yield()`？是否误改了 `proc.c` 调度机制？ |
| `wait4` 返回错 | `reaped=-1`（没找到子进程） | CP③：扫描时 pid 过滤条件写错；或没扫到 ZOMBIE 就 return -1 |
| `wait4` status 错 | `status=-1` 或乱值 | CP③：`copyout2` 没调用，或参数顺序错 |
| `proctest` 直接 panic | `*p` 解引用用户指针 | CP③：注意不要直接 `*status = ...`，必须用 `copyout2` |

## 常见问题（FAQ）

| 现象 | 原因 / 解决 |
|------|------------|
| `proctest` 输出 `getppid FAILED` | CP① 未实现、返回了自己的 pid，或父子关系读取错误 |
| `proctest` 输出 `sched_yield FAILED` | CP② 未复用 `yield()` 或返回值不正确 |
| `proctest` 卡住 | CP③B 锁/睡眠路径错误，或 CP② 误改了调度机制 |
| `proctest` 输出 `wait4 FAILED: reaped=-1` | CP③A 参数语义或 CP③B pid/parent 筛选错误 |
| `proctest` 输出 `wait4 FAILED: status=-1` | CP③B 未写回 xstate，或 CP③A 取错参数槽位 |
| 写回 status 后内核异常 | 绕过了 `copyout2`，或传入地址在当前进程映射中无效 |
| `sched_yield` 后程序不再继续 | CP② 未正确复用 `yield()`，或破坏了 sched/scheduler 的状态约束 |

## 思考题（可选）

下列题目用于加深理解：

1. **`parent` 指针在什么时候设置？孤儿进程（父进程先于子进程退出）的 parent 是谁？** 提示：看 `exit()` 里的 reparent 逻辑。
2. **`sched_yield()` 调用后，当前进程会立刻继续执行吗？什么时候才会再次运行？** 提示：思考 `yield()` 改了什么状态、什么时候调度器才会再选到它。
3. **`wait4` 中为什么不能直接 `*status = np->xstate`？** 提示：`status` 是用户态传入的地址，内核能否安全访问？
4. **`wait4` 的 `pid == -1` 语义如何实现？** 提示：扫描时的过滤条件要兼容两种 pid 含义。
5. **如果 `wait4` 调用时目标子进程还没退出，父进程会怎样？** 提示：看 `wait()` 里的 `sleep` 调用，思考谁会唤醒它。
