## 基础知识

### xv6 调度机制

每个 CPU 启动后跑一个 `scheduler()` 死循环（`kernel/proc.c`）。循环做的事：

```text
1. 调 pick_next_proc() 选一个 RUNNABLE 进程 p
2. acquire(&p->lock)
3. re-check：p->state 还是 RUNNABLE 吗？
4. 把 p->state 改成 RUNNING，记录到 cpu->proc
5. swtch 到 p 的内核上下文，开始执行 p
6. p 主动让出（yield/exit/IO）后，swtch 回到 scheduler
7. release(&p->lock)
```

这个循环本身是**机制**：怎么加锁、怎么切换上下文、怎么更新状态。本 lab 不动它。

`pick_next_proc()` 是**策略**入口：从进程表里选一个进程返回。默认实现是"返回第一个 RUNNABLE"（轮转 RR），改成"返回 priority 最小的 RUNNABLE"就变成优先级调度。本 lab 改的就是这个函数。

### 上下文切换 `swtch`

`swtch(&old_context, &new_context)`（汇编实现在 `kernel/swtch.S`）保存当前寄存器到 `old_context`，从 `new_context` 恢复寄存器并跳转。被调用的视角看，`swtch` 像是一次普通函数返回——只是返回到了别人留下的现场。

`scheduler` 调 `swtch` 切到 p；p 主动让出时调 `swtch` 切回 `scheduler`。两边各自的内核栈各保留一份被冻结的执行点，下次再被调度到时从那里继续。

本 lab 不需要改 `swtch` 或 `sched`，理解它们的角色即可。

### 时钟中断与抢占

xv6 默认是抢占式调度。每次时钟中断：

```text
时钟中断 → usertrap()/kerneltrap() → devintr() 检测到时钟
→ which_dev = 2 → 调用 yield() → 当前进程状态改为 RUNNABLE
→ sched() → swtch 切回 scheduler → scheduler 选下一个进程
```

进程也可以主动让出 CPU（`yield()` 或 `sched_yield`，见 lab2）。无论主动还是被动，最终都通过 `sched` + `swtch` 切换。

### 优先级数值约定

本 lab 约定：**`priority` 数值越小，优先级越高**（与 Linux nice 一致）。

- `priority = 0`：最高优先级
- `priority = N`：数值越大优先级越低
- 默认值（未显式设置）：`allocproc` 时初始化为 0

实际比较时，`pick_next_proc` 应在所有 RUNNABLE 进程中找 `priority` 最小的那一个。

### 机制 vs 策略

| 机制（不改） | 策略（可改） |
|--------------|--------------|
| `scheduler()` 主循环 | `pick_next_proc()` 的选择算法 |
| `swtch` / `sched` | 选择 RUNNABLE 的标准 |
| 加锁、状态转换、re-check | 多个 RUNNABLE 的排序规则 |
| 时钟中断触发 `yield` | 时间片长度（默认固定） |

后续 lab 想做 MLFQ、stride、CFS 等算法，都只需要改 `pick_next_proc` 即可。

### `scheduler()` 主循环源码

```c
void scheduler(void) {
    struct proc *p;
    struct cpu *c = mycpu();
    extern pagetable_t kernel_pagetable;
    c->proc = 0;
    for(;;){
        intr_on();
        p = pick_next_proc();           // 策略入口（CP③）
        if(p) {
            acquire(&p->lock);
            if(p->state == RUNNABLE) {  // re-check：pick 无锁，状态可能已变
                p->state = RUNNING;
                c->proc = p;
                w_satp(MAKE_SATP(p->kpagetable));   // 切到进程内核页表
                sfence_vma();
                swtch(&c->context, &p->context);
                w_satp(MAKE_SATP(kernel_pagetable)); // 切回调度器内核页表
                sfence_vma();
                c->proc = 0;
            }
            release(&p->lock);
        } else {
            intr_on();
            asm volatile("wfi");        // 无可跑进程，等中断
        }
    }
}
```

`re-check` 的意义：`pick_next_proc` 返回的进程，状态可能在 `pick` 之后被别的 CPU 抢走。所以 `scheduler` 拿到锁后要再确认一次 `state == RUNNABLE`，避免运行一个已经被回收或正在睡眠的进程。

`w_satp` / `sfence_vma` 是进程切换时的页表切换：进入进程前切到该进程的内核页表，离开时切回调度器使用的全局内核页表。本 lab 不动这一层。

### 占位的 `pick_next_proc`

```c
struct proc *pick_next_proc(void) {
    struct proc *p;
    for(p = proc; p < &proc[NPROC]; p++) {
        if(p->state == RUNNABLE)
            return p;
    }
    return 0;
}
```

占位实现按进程表顺序返回第一个 RUNNABLE，等价于轮转。CP③ 需要改成在所有 RUNNABLE 进程中找 `priority` 最小的。

### 三个 CP 在调用链中的位置

```text
fork 设 timeslice=0/priority=0
              │
              ▼
set_priority(p) ─→ sys_set_priority ─→ myproc()->priority = p   CP②
set_timeslice(n) ─→ sys_set_timeslice ─→ myproc()->timeslice = n CP①
              │
              ▼
（时钟中断触发 yield，或进程主动让出）
              │
              ▼
scheduler() ─→ pick_next_proc() ─→ 在 RUNNABLE 中找 priority 最小 CP③
              │
              ▼
swtch 切到选中进程
```

CP① ② 设字段，CP③ 用字段。三个 CP 完成后才能体现优先级调度的实际效果。

### 任务3：CP② 实现 `sys_set_priority`

#### 步骤1：理解 `set_priority` 的语义

`set_priority(p)` 把当前进程的 `priority` 设为 `p`。本 lab 约定数值越小优先级越高。

#### 步骤2：实现 `sys_set_priority`

`sys_set_priority`（约 211 行）当前是占位 `return -1;`。实现思路与 CP① 完全相同，只是字段名换成 `priority`。

实现完成后构建运行 `schedtest`，子进程的 `set_priority` 调用应返回 0（不再打印 failed）。但此时 `pick_next_proc` 仍是 RR，三个子进程完成顺序仍是随机的，需要 CP③ 才能体现优先级。

### 任务4：CP③ 改造 `pick_next_proc`

#### 步骤1：阅读占位实现（约 560 行）

```c
struct proc *pick_next_proc(void) {
    struct proc *p;
    for(p = proc; p < &proc[NPROC]; p++) {
        if(p->state == RUNNABLE)
            return p;
    }
    return 0;
}
```

占位版本遇到第一个 RUNNABLE 就返回，没有比较 priority。

#### 步骤2：理解优先级选择算法

改造思路：

1. 遍历整个进程表 `proc[]`，范围 `[proc, &proc[NPROC])`
2. 跳过非 RUNNABLE 的进程
3. 维护一个"当前最优"指针 `best`，初始为 0
4. 对每个 RUNNABLE 进程 `p`：如果 `best == 0` 或 `p->priority < best->priority`，更新 `best = p`
5. 遍历完毕返回 `best`（可能为 0，表示没有可运行进程）

注意比较方向：本 lab 数值越小优先级越高，所以用 `<` 而不是 `>`。

#### 步骤3：实现 `pick_next_proc`

按上述算法替换占位实现。`scheduler` 中的 re-check 不要改。

#### 步骤4：构建运行验收

```bash
make build
make fs
make run
```

在 shell 中执行 `schedtest`，期望输出：

```text
process priority 1 done      ← 最先打印
process priority 2 done
process priority 3 done      ← 最后打印
lab4 test done
观察上方：priority 1 应该最先 done，priority 3 最后
```

看到 priority 1 最先打印即说明优先级调度生效。

## 调试与验证

### 验收点

完成以下三条即视为通过：

1. `schedtest` 中三个子进程按 priority 1 → 2 → 3 顺序完成打印
2. `set_timeslice` / `set_priority` 两个 syscall 都返回 0，子进程不再打印 `set_priority failed`
3. 能完整口述从子进程调用 `set_priority` 到 `pick_next_proc` 选到该进程的整个流程

### 现象分层定位

| 故障层 | 现象 | 排查方向 |
|--------|------|----------|
| syscall 层 | `schedtest` 打印 `set_priority failed` | CP② 没实现，仍返回 -1 |
| 策略层 | 三个子进程顺序随机，priority 1 没最先 | CP③ 没改 `pick_next_proc`，或比较方向写反 |
| 优先级层 | priority 数值越大反而越先跑 | CP③ 用了 `>` 而非 `<`，比较方向反 |
| 系统启动层 | 启动后无 shell | `pick_next_proc` 写错（死循环 / 总返回 0 / 越界） |
| 多核竞争 | 偶发进程丢失 | re-check 是否仍存在？`scheduler` 拿到锁后是否还检查 `state == RUNNABLE`？ |

## 常见问题（FAQ）

| 现象 | 原因 / 解决 |
|------|------------|
| `schedtest` 打印 `set_priority failed` | CP② 没实现，或 `argint` 失败 |
| 三个子进程顺序乱，priority 1 没先完成 | CP③ 没改 `pick_next_proc`，或仍用 RR 占位 |
| priority 数值大的进程反而先跑 | CP③ 比较方向反（`>` 应为 `<`） |
| 系统启动卡死，无 shell | `pick_next_proc` 死循环或总返回 0；检查循环边界和返回值 |
| `make build` 报 `set_priority undeclared` | `sysnum.h` 或 `usys.pl` 没预填（应已预填，检查拼写） |
| 调度策略改了但效果不明显 | `schedtest` 子进程运行时间太短没触发多次调度；可增大循环次数 |

## 思考题（可选）

下列题目用于加深理解：

1. **`pick_next_proc` 无锁返回，为什么 `scheduler` 拿到锁后还要 re-check？** 提示：考虑多核场景下 pick 与 acquire 之间发生的事情。
