## 前置：从 `make run` 到 shell：源码、构建、加载与上电执行

lab0 已经让整个系统跑起来，但没有要求读懂代码。

本 lab 是第一次接触内核源码，在做系统调用实验之前，需要先理解：从你在终端敲下命令开始，代码如何被编译成内核镜像，QEMU 如何按参数搭出一台 RISC-V 机器，镜像如何被加载到内存地址，CPU 又如何从第一条指令一路跑到 shell 提示符。

系统调用链路发生在 shell 就绪之后，而内核启动是这条链路得以存在的前提。只有先知道 shell 是怎么来的，后面才能理解为什么用户输入 `halt` 会触发 `ecall`，为什么内核能接住这个 `ecall`。

### 先分清三件事：源码、构建产物、运行时机器

学生刚接触 xv6 时，最容易把 `.c`、`.S`、`.o`、`target/kernel`、`fs.img`、内存地址混在一起。先记住一个基本事实：**QEMU 不直接读源码，CPU 也不直接读文件**。

```text
源码层：Makefile / .c / .S / .ld
          ↓ 由 make 调用编译器、汇编器、链接器处理
构建层：.o / target/kernel / xv6-user/_init / fs.img
          ↓ 由 QEMU、OpenSBI、xv6 自己加载
运行层：内存地址 / PC / 寄存器 / 机器指令
```

各类文件分别给不同工具看：


| 文件/产物           | 谁使用             | 作用                                   |
| --------------- | --------------- | ------------------------------------ |
| `Makefile`      | `make`          | 描述怎么编译、链接、打包、启动                      |
| `.c`            | C 编译器           | 编译成 RISC-V 机器码对应的 `.o` 目标文件          |
| `.S`            | 汇编器/编译器         | 汇编成 `.o` 目标文件                        |
| `.ld`           | 链接器             | 决定内核各段放到哪些运行地址                       |
| `.o`            | 链接器             | 中间目标文件，不是最终启动镜像                      |
| `target/kernel` | QEMU / OpenSBI  | 最终内核镜像                               |
| `fs.img`        | QEMU + xv6 文件系统 | 虚拟磁盘镜像，里面放 `/init`、`sh`、`halt` 等用户程序 |


所以启动不是“QEMU 读 `main.c`”，也不是“CPU 跳到 `entry_qemu.S` 文件”。真正发生的是：源码先被构建成机器码文件，机器码文件再被加载进内存，CPU 根据 PC 寄存器里的地址去内存取指令执行。

### 本实验实际用到的三个主命令

本 lab 不是只有 `make run` 一个命令。完整实验里至少有三步。

#### 1. 只构建内核和用户程序

```bash
make build platform=qemu
```

`build` 目标在 `Makefile` 中定义为：

```makefile
build: $T/kernel userprogs
```

它做两类事情：

1. 生成内核镜像 `target/kernel`
2. 编译用户程序，例如 `xv6-user/_init`、`xv6-user/_sh`、`xv6-user/_halt`

这一步只负责“把源码变成构建产物”，不会启动 QEMU。

#### 2. 生成 FAT32 文件系统镜像

```bash
make fs platform=qemu
```

内核镜像 `target/kernel` 里不包含所有用户程序。`init`、`sh`、`ls`、`cat`、`halt` 这些用户态程序要放进 `fs.img`，内核启动后再从这个虚拟磁盘里加载它们。

`Makefile` 中的 `UPROGS` 列表包含：

```makefile
UPROGS=\
    $U/_init\
    $U/_sh\
    ...
    $U/_halt
```

`make fs` 会创建或打开 `fs.img`，把这些 `_xxx` 用户程序复制进去。后面 QEMU 用 `-drive file=fs.img,...` 把它挂成虚拟磁盘，xv6 的 `exec()` 才能找到 `/init`、`/sh`、`/halt`。

这也解释了为什么改了用户程序后，有时必须重新 `make fs`：否则新的用户程序还没进入 `fs.img`，shell 里当然找不到或运行的仍是旧版本。

#### 3. 构建并启动 QEMU

```bash
make run platform=qemu
```

`run` 目标写成：

```makefile
run: build
```

意思是：运行前先执行 `build`。所以 `make run platform=qemu` 不是单纯启动 QEMU，它会先保证 `target/kernel` 和用户程序已经编译好，然后再调用 QEMU。

但注意：`run` 依赖 `build`，**不等于自动重新生成** `fs.img`。如果 `fs.img` 不存在，或者你修改了要打包进去的用户程序，仍然需要先执行 `make fs platform=qemu`。

### `platform=qemu` 改变了哪些构建选择

`Makefile` 开头默认是：

```makefile
platform := k210
```

而课程要求使用 QEMU，因此命令里写：

```bash
platform=qemu
```

这会覆盖默认值，让后续 `ifeq ($(platform), qemu)` 相关分支生效。它至少影响四类东西。

#### 1. 选择 QEMU 的入口汇编

```makefile
ifeq ($(platform), k210)
OBJS += $K/entry_k210.o
else
OBJS += $K/entry_qemu.o
endif
```

所以 QEMU 平台用的是 `kernel/entry_qemu.S`，不是 `kernel/entry_k210.S`。

#### 2. 选择 QEMU 的设备驱动

K210 真板子会编译 `spi.o`、`gpiohs.o`、`sdcard.o` 等真实硬件驱动；QEMU 平台会编译：

```makefile
$K/virtio_disk.o
```

这是因为 QEMU 里给 xv6 暴露的是 virtio 块设备，而不是 K210 的 SD 卡控制器。

#### 3. 选择 QEMU 的链接脚本

```makefile
ifeq ($(platform), qemu)
linker = ./linker/qemu.ld
endif
```

`linker/qemu.ld` 决定 QEMU 平台下内核从哪个地址开始布局。

#### 4. 定义 `QEMU` 编译宏

```makefile
ifeq ($(platform), qemu)
CFLAGS += -D QEMU
endif
```

于是代码里的 `#ifdef QEMU` 会走 QEMU 分支。例如 `kernel/include/memlayout.h` 中 QEMU 的 UART 地址是 `0x10000000`，virtio 磁盘地址是 `0x10001000`。这些地址不是 xv6 随便编的，而是 QEMU `virt` 机器规定的内存映射设备地址。

### `make run` 最后展开成哪条 QEMU 命令

QEMU 相关参数在 `Makefile` 中逐步拼出来：

```makefile
QEMUOPTS = -machine virt -kernel $T/kernel -m 128M -nographic
QEMUOPTS += -smp $(CPUS)
QEMUOPTS += -bios default
QEMUOPTS += -drive file=fs.img,if=none,format=raw,id=x0
QEMUOPTS += -device virtio-blk-device,drive=x0,bus=virtio-mmio-bus.0
```

展开后大致是：

```bash
qemu-system-riscv64 \
  -machine virt \
  -kernel target/kernel \
  -m 128M \
  -nographic \
  -smp 2 \
  -bios default \
  -drive file=fs.img,if=none,format=raw,id=x0 \
  -device virtio-blk-device,drive=x0,bus=virtio-mmio-bus.0
```

这些参数不是 xv6 识别的，而是 QEMU 识别的。QEMU 先解析这些参数，再在宿主机进程里模拟出一台 RISC-V 机器。


| 参数                              | 谁识别  | 作用                     |
| ------------------------------- | ---- | ---------------------- |
| `-machine virt`                 | QEMU | 创建 RISC-V `virt` 虚拟开发板 |
| `-kernel target/kernel`         | QEMU | 指定要加载的 xv6 内核镜像        |
| `-m 128M`                       | QEMU | 给虚拟机 128MB 物理内存        |
| `-nographic`                    | QEMU | 不开图形窗口，把串口输入输出接到当前终端   |
| `-smp 2`                        | QEMU | 创建 2 个虚拟 hart          |
| `-bios default`                 | QEMU | 使用 QEMU 内置 OpenSBI 固件  |
| `-drive file=fs.img,...`        | QEMU | 把 `fs.img` 作为后端磁盘文件    |
| `-device virtio-blk-device,...` | QEMU | 把这块磁盘暴露成 virtio 块设备    |


这里也要纠正一个常见误解：QEMU 不是按文件后缀判断“谁是固件、谁是内核、谁是磁盘”。角色由参数决定：`-bios` 后面的是固件，`-kernel` 后面的是内核，`-drive file=...` 后面的是磁盘镜像。

### SBI、OpenSBI、RustSBI：规范和实现不是一回事

仓库里有 `bootloader/SBI/`，里面能看到 RustSBI；但 QEMU 运行时又说用了 OpenSBI。这并不矛盾，因为 **SBI 是规范，OpenSBI 和 RustSBI 是两种实现**。

- SBI（Supervisor Binary Interface）：RISC-V 上 M-mode 固件提供给 S-mode 内核的服务接口规范
- OpenSBI：SBI 的一种实现，QEMU `-bios default` 默认使用它
- RustSBI：SBI 的另一种实现，主要服务 K210 真板子路径

`Makefile` 中确实保留了 RustSBI 的构建目标：

```makefile
RUSTSBI = ./bootloader/SBI/sbi-qemu
```

也有 `RUSTSBI:` 规则去编译 `rustsbi-qemu` 或 `rustsbi-k210`。但是 QEMU 的实际启动参数是：

```makefile
QEMUOPTS += -bios default
```

所以本实验的 QEMU 路径实际使用 QEMU 自带的 OpenSBI，不使用仓库里的 RustSBI。K210 真板子路径才会把 RustSBI 和内核镜像拼在一起烧录。

### 什么叫“加载”：把文件字节搬到内存地址

“加载”不是抽象词，它的意思很具体：**把某个文件里的字节，搬到内存的某个地址范围里**。

本实验里至少有三种加载：


| 加载对象                      | 发生时间        | 谁负责                 | 结果                               |
| ------------------------- | ----------- | ------------------- | -------------------------------- |
| OpenSBI 固件                | QEMU 启动虚拟机时 | QEMU                | 放到 `0x80000000` 附近，作为上电后最先执行的程序  |
| xv6 内核 `target/kernel`    | QEMU 启动虚拟机时 | QEMU / OpenSBI 启动流程 | 放到 `0x80200000` 附近，后续跳入 `_entry` |
| `/init`、`sh`、`halt` 等用户程序 | xv6 已启动后    | xv6 的 `exec()`      | 从 `fs.img` 读入某个用户进程的地址空间         |


所以不要把“加载内核”和“加载用户程序”混在一起：内核是 QEMU 启动时加载的；`/init`、`sh`、`halt` 是 xv6 内核跑起来以后，通过文件系统和 `exec()` 加载的。

### 地址、内存、PC：程序为什么会执行

物理内存可以先粗略理解成一大排按字节编号的小格子。每个格子有一个编号，这个编号就是地址。

```text
地址             内容
0x80000000       OpenSBI 的某个机器码字节
0x80000001       OpenSBI 的下一个字节
...
0x80200000       xv6 内核入口附近的机器码字节
```

CPU 里有一个非常关键的寄存器叫 PC（Program Counter，程序计数器）。PC 保存“下一条要执行的指令地址”。CPU 的基本工作循环是：

```text
1. 根据 PC 里的地址去内存取机器码字节
2. 把字节解码成指令
3. 执行指令
4. 更新 PC，指向下一条指令
```

因此“程序运行”的本质不是“运行某个文件”，而是：文件里的机器码字节已经被加载到内存，PC 指向其中某个地址，CPU 不断取指、解码、执行。

这也是为什么后面要关心 `0x80000000` 和 `0x80200000`：它们不是普通数字，而是 CPU 取指时会使用的内存地址。

### 链接脚本如何决定 xv6 内核地址

QEMU 平台使用 `linker/qemu.ld`。其中两行最关键：

```ld
ENTRY(_entry)
BASE_ADDRESS = 0x80200000;
```

`BASE_ADDRESS = 0x80200000` 表示链接器按照“内核从 `0x80200000` 开始运行”这个假设来安排 `.text`、`.rodata`、`.data`、`.bss` 等段：

```ld
. = BASE_ADDRESS;
.text : {
    *(.text .text.*)
    ...
}
```

`ENTRY(_entry)` 表示内核入口符号是 `_entry`。链接器会把 `entry_qemu.o`、`main.o`、`proc.o` 等目标文件合成一个整体 `target/kernel`，并记录各个符号的运行地址。OpenSBI 后面跳转的不是“某个源码文件”，而是 `_entry` 这个符号对应的机器码地址。

### 本节完整时间线

前面的内容解释了“命令、构建、QEMU 参数、加载、地址和 PC”。接下来才进入传统意义上的启动流程。按时间顺序，完整链路是：

```text
① 你输入 make build / make fs / make run platform=qemu
② make 读取 Makefile，选择 QEMU 分支，编译链接出 target/kernel，打包 fs.img
③ QEMU 解析 -machine/-kernel/-smp/-bios/-drive 等参数，搭出 RISC-V virt 虚拟机
④ QEMU 加载 OpenSBI 和 target/kernel，创建 2 个 hart 和 128MB 内存
⑤ 虚拟 CPU 上电，PC 指向 0x80000000，开始执行 OpenSBI（M-mode）
⑥ OpenSBI 跳转到内核入口 _entry（S-mode 第一条指令，约 0x80200000）
⑦ _entry 设置栈，调用 main()
⑧ main() 依次调用 init 函数，完成内核各子系统初始化
⑨ userinit() 创建第一个用户进程，scheduler() 通过 swtch 切换过去
⑩ initcode 执行 ecall 触发 exec("/init")，init 进程 fork 出 shell
```

### 阶段一：QEMU 上电与 OpenSBI

执行 `make run platform=qemu` 时，最终调用的命令包含 `-bios default`，这会让 QEMU 加载内置的 OpenSBI 固件。QEMU 的 RISC-V virt 机器启动时，所有 hart（硬件线程）的复位地址是 `0x80000000`，OpenSBI 就加载在这个位置。

OpenSBI 运行在 M-mode（Machine Mode），负责：

- 初始化 M-mode 的 CSR（`mstatus`、`mepc` 等）
- 配置 PMP（Physical Memory Protection），允许 S-mode 访问全部内存
- 将下一个阶段的入口地址写入 `mepc`，执行 `mret` 把控制权交给 S-mode

QEMU virt 机器约定，S-mode 的加载地址是 `0x80200000`。这个值出现在链接脚本 `linker/qemu.ld` 中：

```
BASE_ADDRESS = 0x80200000;
```

OpenSBI 跳转的目标地址就是 `0x80200000`，也就是内核的 `.text` 段起始位置。此后 CPU 进入 S-mode，开始执行内核代码。

### 阶段二：内核入口 _entry

`0x80200000` 处的代码是 `kernel/entry_qemu.S` 中的 `_entry` 标号，由链接脚本的 `ENTRY(_entry)` 指定为入口。这个文件很短：

```asm
    .section .text
    .globl _entry
_entry:
    add t0, a0, 1
    slli t0, t0, 14
    la sp, boot_stack
    add sp, sp, t0
    call main

loop:
    j loop

    .section .bss.stack
    .align 12
    .globl boot_stack
boot_stack:
    .space 4096 * 4 * 2
    .globl boot_stack_top
boot_stack_top:
```

这段代码做的事情：

1. OpenSBI 在跳转时把 hartid 放在 `a0` 寄存器中传入。`add t0, a0, 1` 和 `slli t0, t0, 14` 计算出当前 hart 的栈偏移量：hart 0 用 `boot_stack + 16KB`，hart 1 用 `boot_stack + 32KB`。每个 hart 各自有一块 16KB 的栈空间
2. `la sp, boot_stack` 加载栈底地址，`add sp, sp, t0` 加上偏移量得到当前 hart 的栈顶
3. `call main` 跳转到 C 代码的 `main()` 函数

`boot_stack` 分配在 `.bss.stack` 段，大小是 `4096 * 4 * 2 = 32KB`，刚好容纳两个 hart 各 16KB。QEMU 配置了双核（`-smp 2`），两个 hart 都会经过 `_entry` 进入 `main()`。

如果 `main()` 意外返回（不应该发生），`j loop` 构成一个死循环兜底。

### 阶段三：main() 的初始化序列

`main()` 函数在 `kernel/main.c` 中。hart 0 和 hart 1 走不同分支：hart 0 执行全部初始化，hart 1 等待 hart 0 完成后做少量配置。以下是 hart 0 的初始化调用序列：

```c
void
main(unsigned long hartid, unsigned long dtb_pa)
{
  inithartid(hartid);

  if (hartid == 0) {
    consoleinit();
    printfinit();
    print_logo();
    kinit();         // physical page allocator
    kvminit();       // create kernel page table
    kvminithart();   // turn on paging
    timerinit();
    trapinithart();  // install kernel trap vector
    procinit();
    plicinit();
    plicinithart();
    disk_init();
    binit();         // buffer cache
    fileinit();      // file table
    userinit();      // first user process
    /* ... 唤醒其他 hart ... */
    started = 1;
  }
  else { /* hart 1 的初始化 */ }

  scheduler();
}
```

这 13 个 init 函数按功能分组：


| 分组    | 函数                         | 职责                                                                  |
| ----- | -------------------------- | ------------------------------------------------------------------- |
| 控制台   | `consoleinit`、`printfinit` | 初始化串口控制台和 `printf` 的锁，此后内核可以打印输出                                    |
| 物理内存  | `kinit`                    | 初始化物理页分配器（`kalloc`/`kfree` 的底层），管理从 `kernel_end` 到 `PHYSTOP` 的空闲物理页 |
| 虚拟内存  | `kvminit`、`kvminithart`    | `kvminit` 创建内核页表，建立内核地址空间的映射；`kvminithart` 把页表基地址写入 `satp` 寄存器，开启分页 |
| 中断与陷阱 | `timerinit`、`trapinithart` | `timerinit` 初始化定时器；`trapinithart` 把 `stvec` 设为内核陷阱入口，此后异常和中断能被捕获    |
| 进程    | `procinit`                 | 初始化进程表 `proc[]` 数组，给每个进程结构体加上锁                                      |
| 外设    | `plicinit`、`plicinithart`  | 初始化 PLIC（Platform-Level Interrupt Controller），配置设备中断的使能和优先级         |
| 块设备   | `disk_init`、`binit`        | `disk_init` 初始化 virtio 磁盘；`binit` 初始化缓冲区缓存（buffer cache），加速磁盘读写     |
| 文件    | `fileinit`                 | 初始化全局文件表                                                            |
| 第一个进程 | `userinit`                 | 创建系统中第一个用户进程（initcode），是整个启动流程从内核态转入用户态的关键一步                        |


hart 0 完成 `userinit()` 后，通过 SBI 发送 IPI（核间中断）唤醒 hart 1，然后把 `started` 置为 1。hart 1 在 `while (started == 0)` 处自旋等待，收到信号后执行 `kvminithart`、`trapinithart`、`plicinithart` 完成自身的页表和中断配置。

两个 hart 最终都会到达 `scheduler()`，进入调度器主循环。

### 阶段四：userinit() 与第一个用户进程

`userinit()` 在 `kernel/proc.c` 第 285 行，负责创建系统中第一个用户进程：

```c
void
userinit(void)
{
  struct proc *p;

  p = allocproc();
  initproc = p;

  uvminit(p->pagetable, p->kpagetable, initcode, sizeof(initcode));
  p->sz = PGSIZE;

  p->trapframe->epc = 0x0;
  p->trapframe->sp = PGSIZE;

  safestrcpy(p->name, "initcode", sizeof(p->name));
  p->state = RUNNABLE;

  release(&p->lock);
}
```

`allocproc()` 在进程表中找到一个 `UNUSED` 的槽位，分配 trapframe 页和页表，把进程上下文的 `ra` 寄存器设为 `forkret`（阶段五会讲到）。`initcode` 是一段硬编码的字节数组，定义在同一个文件中：

```c
uchar initcode[] = {
  0x17, 0x05, 0x00, 0x00, 0x13, 0x05, 0x45, 0x02,
  0x97, 0x05, 0x00, 0x00, 0x93, 0x85, 0x35, 0x02,
  0x93, 0x08, 0x70, 0x00, 0x73, 0x00, 0x00, 0x00,
  0x93, 0x08, 0x20, 0x00, 0x73, 0x00, 0x00, 0x00,
  0xef, 0xf0, 0x9f, 0xff, 0x2f, 0x69, 0x6e, 0x69,
  0x74, 0x00, 0x00, 0x24, 0x00, 0x00, 0x00, 0x00,
  0x00, 0x00, 0x00, 0x00
};
```

这串字节对应的汇编代码就是 `xv6-user/initcode.S`：

```asm
.globl start
start:
        la a0, init
        la a1, argv
        li a7, SYS_exec
        ecall

exit:
        li a7, SYS_exit
        ecall
        jal exit

init:
  .string "/init\0"

.p2align 2
argv:
  .long init
  .long 0
```

initcode 的作用是执行 `exec("/init", {"/init", 0})`。它把 `SYS_exec` 放入 `a7`，参数字符串 `"/init"` 的地址放入 `a0`，argv 数组地址放入 `a1`，然后执行 `ecall` 陷入内核。

`uvminit` 把这段 initcode 拷贝到用户地址空间的第 0 页。`trapframe->epc = 0x0` 意味着进程从地址 0 开始执行，也就是 initcode 的 `start` 标号处。`trapframe->sp = PGSIZE` 把用户栈顶设在这一页的末尾（栈向下生长）。

此时进程状态被设为 `RUNNABLE`，等待调度器选中。

### 阶段五：scheduler() 与 swtch

`main()` 最后调用 `scheduler()`，进入调度器的主循环（`kernel/proc.c` 第 534 行）：

```c
void
scheduler(void)
{
  struct proc *p;
  struct cpu *c = mycpu();
  extern pagetable_t kernel_pagetable;

  c->proc = 0;
  for(;;){
    intr_on();

    int found = 0;
    for(p = proc; p < &proc[NPROC]; p++) {
      acquire(&p->lock);
      if(p->state == RUNNABLE) {
        p->state = RUNNING;
        c->proc = p;
        w_satp(MAKE_SATP(p->kpagetable));
        sfence_vma();
        swtch(&c->context, &p->context);
        w_satp(MAKE_SATP(kernel_pagetable));
        sfence_vma();
        c->proc = 0;
        found = 1;
      }
      release(&p->lock);
    }
    if(found == 0) {
      intr_on();
      asm volatile("wfi");
    }
  }
}
```

调度器遍历进程表，找到 `RUNNABLE` 状态的进程，将其设为 `RUNNING`，然后调用 `swtch(&c->context, &p->context)` 完成上下文切换。

`swtch` 的实现在 `kernel/swtch.S` 中，它保存当前寄存器组到 `c->context`（调度器上下文），从 `p->context` 加载寄存器组。前面阶段三提到，`allocproc()` 把 `p->context.ra` 设为了 `forkret`，因此 `swtch` 结尾的 `ret` 指令会跳转到 `forkret`：

```c
void
forkret(void)
{
  static int first = 1;

  release(&myproc()->lock);

  if (first) {
    first = 0;
    fat32_init();
    myproc()->cwd = ename("/");
  }

  usertrapret();
}
```

`forkret` 第一次被调用时（`first == 1`），完成文件系统的初始化（`fat32_init`）并设置当前进程的工作目录。然后调用 `usertrapret()`，这个函数把 trapframe 中保存的寄存器恢复到用户态寄存器，执行 `sret` 指令从 S-mode 返回 U-mode。CPU 从此运行在用户态，PC 指向 `trapframe->epc` 的值（0x0），开始执行 initcode。

### 阶段六：exec("/init") 与 shell 启动

initcode 在用户态执行 `ecall`，触发 `SYS_exec` 系统调用。内核的 `exec()` 函数（`kernel/exec.c` 第 44 行）负责加载 `/init` 程序。exec 的关键步骤：

1. 调用 `ename(path)` 在文件系统中找到 `/init` 对应的目录项
2. 读取 ELF 头，验证魔数
3. 遍历 ELF 程序段，用 `uvmalloc` 分配用户页，用 `loadseg` 把段内容从磁盘读入物理页
4. 在用户地址空间顶部分配两页作为用户栈，把 argv 字符串压入栈中
5. 把 `trapframe->epc` 设为 ELF 入口地址（即 `/init` 程序的 `main` 函数地址），`trapframe->sp` 设为用户栈顶
6. 替换进程的页表，丢弃旧的地址空间

exec 返回后，进程的地址空间已经完全变成 `/init` 程序的内容。此后控制权返回用户态，从 `/init` 的 `main` 函数开始执行。

`/init` 程序的源码是 `xv6-user/init.c`：

```c
char *argv[] = { "sh", 0 };

int
main(void)
{
  int pid, wpid;

  dev(O_RDWR, CONSOLE, 0);
  dup(0);  // stdout
  dup(0);  // stderr

  for(;;){
    printf("init: starting sh\n");
    pid = fork();
    if(pid < 0){
      printf("init: fork failed\n");
      exit(1);
    }
    if(pid == 0){
      exec("sh", argv);
      printf("init: exec sh failed\n");
      exit(1);
    }

    for(;;){
      wpid = wait((int *) 0);
      if(wpid == pid){
        break;
      } else if(wpid < 0){
        printf("init: wait returned an error\n");
        exit(1);
      }
    }
  }
}
```

init 进程做了三件事：

1. 打开控制台设备（文件描述符 0），`dup` 两次得到 fd 1（stdout）和 fd 2（stderr），这样标准输入/输出/错误都指向控制台
2. `fork()` 创建子进程，子进程调用 `exec("sh", argv)` 把自身替换为 shell 程序
3. 父进程在 `wait()` 中等待。如果 shell 退出，回到 `for(;;)` 循环重新 fork 一个新 shell；如果 shell 的某个子进程（无父进程的孤儿）退出，继续等待

shell（`sh`）启动后，打印提示符 `$`，读取用户输入的命令。至此，从上电到 shell 的完整启动流程结束。

### 从 shell 到系统调用的衔接

shell 运行起来之后，用户输入的每一条命令都可能触发系统调用。以本 lab 要实现的 `halt` 命令为例：

1. shell 读取到 `halt`，在文件系统中找到 `/halt` 程序
2. shell 调用 `fork()` 创建子进程，子进程 `exec("/halt")` 加载 halt 程序
3. halt 程序的 `main()` 调用 `halt()`——这正是本 lab 要接通的链路
4. `halt()` 通过用户态桩执行 `ecall`，控制权进入内核陷阱处理
5. 内核分发到 `sys_halt`，调用 `sbi_shutdown` 关机

从内核启动的角度看，整个 syscall 机制的搭建发生在阶段三的 `trapinithart()`（设置 `stvec`）和 `procinit()`（创建进程结构）中。阶段四的 `userinit` 让第一个用户进程具备了触发 `ecall` 的条件。阶段六的 initcode 本身就在执行一次 syscall（`SYS_exec`）。

至此可以进入"基础知识"小节，详细了解 syscall 链路的每个环节。

## 基础知识



### RISC-V 特权级

RISC-V 定义多个特权级，本 lab 涉及三个：

- M-mode（Machine）：最高特权，硬件初始化阶段运行于此。OpenSBI 固件也运行于此
- S-mode（Supervisor）：xv6-k210 内核运行的特权级
- U-mode（User）：用户程序（init、sh、halt 等）运行的特权级

不同特权级有不同的可执行指令集和可访问资源。用户态不能直接调用内核函数，也不能直接访问硬件，必须通过受控的入口陷入内核。这种"受控入口"就是 `ecall` 指令。

### `ecall` 指令

`ecall` 是 RISC-V 的环境调用指令，作用是主动触发一个异常，请求更高特权级的服务。在用户态执行 `ecall` 时，CPU 会：

1. 把当时的 PC 保存到 `sepc` 寄存器
2. 跳转到 `stvec` 寄存器指向的陷阱处理入口（内核预先设置好的）
3. 切换到 S-mode

控制权转入内核后，内核通过读 `scause` 判断这次陷入的原因。系统调用对应的 `scause` 值为 8（environment call from U-mode）。

### xv6 系统调用链路

xv6-k210 中一次系统调用的完整路径如下：

```text
用户程序调用 halt()
        ↓
usys.pl 生成的用户态桩 halt: li a7,SYS_halt; ecall; ret
        ↓ ecall 触发陷阱
trap.c: usertrap() 检测到 scause==8，调用 syscall()
        ↓
syscall.c: syscall() 读 a7 作 num，调 syscalls[num]()
        ↓ 按 SYS_halt 找到
sysproc.c: sys_halt() 内核实现
        ↓ 关机场景
sbi.h: sbi_shutdown() 通过 ecall 请求 M-mode 关机
```

链路涉及五个文件，分别承担五种角色：


| 角色    | 文件                        | 作用                                 |
| ----- | ------------------------- | ---------------------------------- |
| 用户态调用 | `xv6-user/halt.c`         | 用户程序调用 `halt()`                    |
| 用户态桩  | `xv6-user/usys.pl`        | 生成汇编桩，把 syscall 号放进 `a7` 并 `ecall` |
| 用户态原型 | `xv6-user/user.h`         | `halt` 的函数原型，让 C 代码能调用             |
| 编号    | `kernel/include/sysnum.h` | 定义 `SYS_halt` 编号                   |
| 分发    | `kernel/syscall.c`        | 把编号映射到 `sys_halt` 函数指针             |
| 内核实现  | `kernel/sysproc.c`        | `sys_halt` 的实际代码                   |
| 底层服务  | `kernel/include/sbi.h`    | `sbi_shutdown` 等封装                 |


后续 lab 加新 syscall 时，前五项必须同步修改，缺一项链路就断。`sbi.h` 这一层只在涉及底层服务时才用（如关机、定时器）。

### `a7` 寄存器与系统调用编号

`ecall` 只负责陷入，并不携带"调用哪个系统调用"的信息。xv6 的约定是：陷入前把系统调用编号放进 `a7` 寄存器，内核的 `syscall()` 读 `a7`，用编号作为下标查 `syscalls[]` 数组，找到对应的内核函数。

因此系统调用编号必须满足两条：

- 与现有编号不冲突（否则两个 syscall 会被映射到同一个内核函数）
- 不超出 `syscalls[]` 数组的边界（`syscall.c` 中 `num < NELEM(syscalls)` 检查）



### SBI 与 `sbi_shutdown`

关机是典型的"用户态做不了"的操作。内核本身也没有直接关机的能力，必须通过 SBI 请求 M-mode 完成。`kernel/include/sbi.h` 中提供了若干 SBI 调用的 C 内联封装，其中 `sbi_shutdown()` 通过 `ecall` 请求 OpenSBI 关闭机器。QEMU 收到关机请求后立即退出。

### `syscall()` 分发流程

`kernel/syscall.c` 的 `syscall()` 函数（约 205 行）：

```c
void syscall(void) {
  int num;
  struct proc *p = myproc();
  num = p->trapframe->a7;
  if(num > 0 && num < NELEM(syscalls) && syscalls[num]) {
    p->trapframe->a0 = syscalls[num]();   // 调用对应内核函数
    ...
  } else {
    printf("pid %d %s: unknown sys call %d\n", ...);
    p->trapframe->a0 = -1;                // 未知 syscall 返回 -1
  }
}
```

三个条件缺一不可：

- `num > 0`：合法编号必须为正
- `num < NELEM(syscalls)`：不越界
- `syscalls[num]`：该编号已注册

未注册的 syscall 会落到 else 分支，返回 -1，并打印 unknown sys call。这正是 CP① 没填对、CP③ 没注册时的现象。

### CP① ~ CP④ 在链路中的位置

```text
                    CP①  CP②          CP③        CP④
                     │    │            │          │
halt() ─→ usys.S ─→ │ a7 │ ─→ ecall ─→ │ dispatch │ ─→ sys_halt() ─→ sbi_shutdown()
                     │    │            │          │
              sysnum.h   usys.pl    syscall.c   sysproc.c
```

四个 CP 顺序闯关：

- **CP①** `sysnum.h`：分配一个未占用的 syscall 编号给 `SYS_halt`
- **CP②** `usys.pl`：在脚本末尾加 `entry("halt")`，让构建时生成 `halt` 用户态桩
- **CP③** `syscall.c`：在 `syscalls[]` 数组中加一项 `[SYS_halt] sys_halt`
- **CP④** `sysproc.c`：实现 `sys_halt()`，调用 `sbi_shutdown()`

每一步在前一步的基础上接通链路。`user.h` 中的 `void halt(void)` 原型已经预填，不需要学生改。

`include/sbi.h` 提供多个 SBI 调用封装（console、timer、ipi、shutdown 等）。`sbi_shutdown()` 是其中之一。

#### 步骤3：替换占位实现

在 `sys_halt` 中调用 `sbi_shutdown()` 完成关机。`sbi_shutdown()` 不返回，但 C 语法要求函数有返回值，因此末尾保留 `return 0;` 满足编译要求。

实现完成后重新构建运行：

```bash
make build platform=qemu
make fs platform=qemu   # 仅当 halt 程序路径或名称变化时才需要重新打包
make run platform=qemu
```



### 任务6：验收



#### 步骤1：在 shell 中执行 halt

```text
-> / $ halt
```

期望现象：QEMU 立即退出，不打印 "should not reach here"，也不出现 panic。

若看到 "should not reach here"：说明 `sys_halt` 内部没有真正触发关机，回到 CP④ 检查实现。

若 QEMU 卡住不动：说明 syscall 编号错或 dispatch 没命中，回到 CP① / CP③ 检查。

#### 步骤2：解释链路

向自己或助教口述：用户态 `halt()` → usys.S 桩 → `ecall` → `usertrap` → `syscall()` → `sys_halt` → `sbi_shutdown` → QEMU 退出。能完整讲清即通过。

## 常见问题（FAQ）


| 现象                                               | 原因 / 解决                                                           |
| ------------------------------------------------ | ----------------------------------------------------------------- |
| `make build` 报 `undefined reference to sys_halt` | `syscalls[]` 中引用了 `sys_halt`，但 `sysproc.c` 中没有该函数。检查函数名拼写         |
| `make build` 报 `'SYS_halt' undeclared`           | `sysnum.h` 中 `SYS_halt` 宏没定义，或拼写与 `syscall.c` 中使用的不一致             |
| shell 跑 `halt` 打印 "should not reach here"        | `sys_halt` 没真正调 `sbi_shutdown`，回 CP④                              |
| shell 跑 `halt` 后 QEMU 卡住无反应                      | syscall 编号错或 dispatch 没命中。回 CP① / CP③                             |
| `pid X sh: unknown sys call N`                   | `SYS_halt` 编号 N 与现有冲突，或 `syscalls[]` 没注册，回 CP① / CP③              |
| `make fs` 报错找不到 `_halt`                          | `Makefile` 中 `UPROGS` 列表是否包含 `$U/_halt`？没构建出 halt 程序就无法打包进 fs.img |

## 思考题（可选）

下列题目用于加深理解：

1. **为什么 syscall 用整数编号，而不是直接用函数名字符串？** 提示：用户态陷入内核时只能用寄存器传少量信息，字符串需要内存地址和长度两个参数，且内核需要做字符串匹配；整数是 O(1) 数组下标查找。
2. `ecall` **之后控制权经历了哪些路径才返回用户态？** 提示：`uservec` → `usertrap` → `syscall` → 内核函数 → `usertrapret` → `sret` 回到用户态。
3. **如果** `syscalls[]` **中漏掉** `[SYS_halt]`**，跑** `halt` **会怎样？** 提示：看 `syscall()` 的 else 分支会做什么。
4. **为什么用户程序不能直接调** `sbi_shutdown`**？** 提示：SBI 是 M-mode 服务，用户态在 U-mode，没有权限直接 `ecall` 到 M-mode。
5. `halt` **用户程序中** `printf("should not reach here")` **这行什么时候会打印？** 提示：思考 `sbi_shutdown` 之后控制流是否会回到 `halt` 程序。
