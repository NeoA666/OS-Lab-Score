● 这个问题问得非常好——它表面是"打印一行字"，底下其实是一次完整的"用户态 → 内核 →
  硬件"往返。我先看一眼 cat
  这个程序本身的源码，再讲给你，保证每个环节都能指到真实文件。

  Thought for 10s, read 1 file (ctrl+o to expand)

● 对，从屏幕上看它确实"只是把 README 的内容又印了一遍"。但这一下背后，是一场完整
  的"用户程序求内核帮忙"的接力。我先把你已经看到的现象，和它真正发生的动作对上。

  一句话回答： cat README 不是 cat 自己"知道"文件内容然后念出来，而是 cat
  这个用户程序通过系统调用，一次次向内核要数据，内核去磁盘上把字节搬出来，再经控
  制台吐到屏幕。

  看 cat 的源码（xv6-user/cat.c），它总共就干了三件事：

  1. open（第 35 行）：open(argv[i], 0) 打开
     README，拿到一个"文件描述符"（一个小整数编号，之后靠它指代这个文件）；
  2. read / write 循环（第 12~13 行）：read(fd, buf, 512)
     从文件里读一块到缓冲区，然后 write(1, buf, n) 把这块写到"1
     号文件描述符"——也就是标准输出（屏幕）；
  3. close（第 40 行）：读完关掉。

  看到关键了吗：cat 从头到尾没有直接碰过磁盘。它只会喊三个词——open、read、write
  。这三个词叫系统调用。

  这里就是深层逻辑，也是全课最核心的一个概念： 用户程序（cat）运行在
  U-mode（用户态），它是没权限也没能力直接操作硬件的。文件内容真身躺在 fs.img
  那块"假磁盘"里，而"从磁盘读数据"这件脏活累活，只有内核（S-mode）能干。所以流程
  是：

  cat（用户态）  --open/read/write-->  内核（S-mode）  --读 virtio 磁盘-->
  fs.img
        ^                                                            |
        +------------------  字节数据原路返回  <----------------------+

  cat 的每一次 read，都会让 CPU 从用户态"掉进"内核态（专业叫 trap /
  ecall），由内核的文件系统代码去磁盘上取一批数据，再切回用户态交给 cat；cat
  拿到后再 write 出去，write 又会掉进内核，由内核把数据送到串口控制台，最终 QEMU
  打印到你的终端。

  所以"打印一遍"是结果，真正的过程是：cat 反复地在用户态和内核态之间来回横跳，靠
  系统调用借内核的手去碰磁盘和屏幕。这条"用户态 → 内核 → 硬件 →
  回来"的往返，就是操作系统存在的意义本身。

  到这里先停一下。你现在可能想知道：read
  这一声喊出去，内核内部具体是怎么一层层（路径解析 → 打开文件 → 缓冲区 → virtio
