① "拼成"到底是干什么的

我先给你看真东西。linker/qemu.ld 开头几行：

OUTPUT_ARCH(riscv)
ENTRY(_entry)              ← 整个内核从哪条指令开始执行

SECTIONS
{
    . = BASE_ADDRESS;      ← 从 0x80200000 开始往下摆

关键在于：每个 .o 在被编译出来的时候，并不知道自己将来会被放在哪。
编译器只管翻译这一个文件，它对"别人在哪、我在哪"一无所知。所以每个 .o
里都留着一堆坑——"这里要调用 printf，可是 printf 的地址我还不知道，先空着"。

链接器干的活就是三步：

1. 按 qemu.ld 说的，从 0x80200000 开始，把
.text（代码）、.rodata（只读数据）、.data、.bss 一段一段摆进内存；
2. 每摆完一段，就记下它的真实地址；
3. 回头把所有 .o 里那些空着的坑，一个个填上真实地址。

填完之后，printf 在哪儿、main
在哪儿，每条指令都清清楚楚——这才成了一个能跑的完整内核。

这不是我嘴上说说，target/kernel.sym 里就是证据：

0000000080200000 .text      ← 代码段被摆在 0x80200000
0000000080209000 .rodata    ← 只读数据紧跟其后
000000008020a000 .data
000000008020b000 .bss

这些地址不是随便来的，就是 qemu.ld 第 4 行那个 0x80200000 一路排下来的结果。所
以链接脚本的作用就一句话：它是一张"谁摆在哪儿"的施工图，链接器照着它施工。

② 高级语言 vs 汇编

一条从"离人近"到"离机器近"的阶梯：

                     长什么样                  谁能看懂
 C（高级语言）     a = b + c;    人一看就懂，机器完全看不懂
 汇编（低级语言）  add a0, a1,   一条对一条 CPU
                   a2            指令，还是文本，人勉强能读
 机器码（.o 里）   一串二进制    CPU 唯一认得的东西

编译器就是把上面那层翻译成下面那层。

"高级"的意思是：不绑定具体 CPU。 你写的 C，换成 x86、换成 ARM
都还能编译。而汇编是绑死在某一种 CPU 上的——RISC-V 的汇编拿到 x86 上，x86
完全不认识。

回答你那句"高级语言是啥？C 代码吗"：对，C 就是高级语言。

所以 ISA 到底是什么

一句话：ISA 是硬件和软件之间的一份合同（约定）。

CPU 这边承诺："你按这套规矩给我指令，我就执行。"编译器这边承诺："我只生成这套

芯片跑，编出来的东西在各自架构内部通用。

打个比方：ISA 就像插座标准。标准定了，哪个厂生产的插头都能插进哪个厂的插座——但
插座内部是铜片还是别的，厂家自己决定。标准是统一的，"怎么实现"是自由的。
这就是为什么叫"架构"而不是"某一颗芯片"。

（严格说还有个小尾巴：架构内部还有"扩展指令"，要看扩展是否一致。但主干是通用的

uint64

  return 0;         ← 永远走不到这行

sbi_shutdown() 一调，机器就关了，根本回不来，所以 return 0; 是死代码。

#### User

还有，桩到底是什么，怎么理解它

#### Claude

"桩"是英文 stub 翻译过来的。stub
本意是"树桩"——树被砍掉之后，留在那儿的那一截。

编程里借这个词，表示"一段短短的、自己什么实事都不干的代码"。

一句话

桩是一段"只负责转交、不干实事"的小函数。
它存在的唯一目的，是让用户程序能像调普通函数一样发起系统调用。

为什么必须有它

用户程序想关机，但它面临两个障碍：

1. 没权限——用户态碰不到硬件
2. 不会写——发起系统调用要手动写汇编（把号塞进 a7、执行
ecall），这对写用户程序的人来说太底层了

所以内核给它开了个"长得像普通函数"的入口。你只管写 halt()，剩下的桩替你办：

halt:                    ← 这个就是桩
 li a7, SYS_halt         ←   把号放进 a7
 ecall                   ←   敲门，进内核
 ret                     ←   （如果内核返回了）返回

用户程序看到的是 halt() 这个函数；桩的真实身份是一段转接代码。

打比方：你想进一栋楼办事，但你进不去。门口有个传达室——你只要说"我办 27 号业务"
，它替你往里递。传达室本身不办业务，它只是那个"接口点"。这个接口点，就是桩。

在本实验里的位置

桩不是手写的，是生成的。xv6-user/usys.pl:9-16 那个 entry() 就是一个"桩工厂"：

entry("fork");     → 生成 fork 的桩
entry("rename");   → 生成 rename 的桩
entry("halt");     ← 你加的这行，生成 halt 的桩

17 个 entry(...)，生成 17 个长得一模一样的桩，只有里面的号不同。

把整条链路串起来看

用户程序调 halt()
      ↓
[桩]  li a7, 27 / ecall / ret        ← usys.S（用户态，只敲门）
      ↓ ecall
[分发] syscall() 看号 → 查表          ← syscall.c（内核态，只看号转交）
      ↓
[真身] sys_halt() → sbi_shutdown()   ← sysproc.c（内核态，真干活）

三层三种角色：桩负责敲门，分发负责转交，真身负责干活。中间靠"号"（27）牵着。

这个uint64是什么。为啥都要返回它

#### Claude

uint64 不是什么新类型，它是 unsigned long 的别名。定义就在
kernel/include/types.h:12：

typedef unsigned long uint64;

拆开看名字：unsigned（无符号，没有负数）+ int + 64（位）。所以它能表示 0 ~
2⁶⁴-1。

（顺带解掉"为什么要起个别名"：unsigned long 这个名字不告诉你它到底几位宽——32
位机器上是 32 位，64 位机器上是 64 位。写成 uint64，意思就钉死了。）

为什么 sys_ 函数全都返回它

两个原因，第二个更硬。

原因一：返回值要放进 a0 寄存器。

kernel/syscall.c:212    p->trapframe->a0 = syscalls[num]();

syscall 干完活，结果是通过 a0 寄存器交还给用户程序的。而 RISC-V 64
的寄存器就是 64 位宽——一个寄存器刚好装一个
uint64。返回值比它大，装不下；比它小，浪费。

原因二：数组的类型强制要求。

kernel/syscall.c:121    static uint64 (*syscalls[])(void) = {

这句话里 uint64 和 (void) 是在说："这个数组里装的，都是不接参数、返回 uint64
的函数。"

所以这不是"大家都习惯这么写"，而是类型上必须一致。你要往这个数组里放一个返回
int 的函数，编译器当场报错。

返回值是拿来干嘛的

它就是 syscall 报给用户程序的结果：

    函数          返回什么
 sys_getpid  当前进程的 pid
 sys_fork    子进程的 pid
 sys_read    实际读到了多少字节
 出错时      -1

所以 halt 那个 return 0，如果真能执行到，用户程序会从 a0 读到
0——只不过它永远执行不到。

（一个小尾巴：uint64 是无符号的，那 -1 怎么存？答案是存成 64 个
1，用户程序按有符号读就是 -1。这个先知道有这么回事就行。）

谁在搬？预处理器

在真正编译之前，还有一个预处理步骤。它专门负责这类"以 # 开头的命令"：

- #include → 把文件内容搬过来
- #define SYS_halt 27 → 做文字替换（还记得那个 27
是怎么钻进机器码的吗？就是它干的）

预处理跑完，才轮到编译器上场。

为什么非得搬

因为 C 有个死规矩：先声明，后使用。

编译器读到 halt(); 这一行时，它必须已经见过 halt
的说明——"这函数接什么参数、返回什么"。没见过就直接报错，说你不认识它。

所以 halt.c 必须在调用之前把说明搬进来：

#include "user.h"     ← 先把 halt 的说明搬过来

int main(void) {
  halt();             ← 现在编译器认识了，能用
  ...
}
