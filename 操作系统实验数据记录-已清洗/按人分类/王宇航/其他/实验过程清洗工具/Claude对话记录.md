### Turn 4

#### User

make builg到底在编什么，为什么不能用机器上普通的gcc

#### Claude

这两个问题其实是同一个问题的两面，我一起讲，因为答案都在一个词上：指令集（ISA
）。

一句话回答： make build 编的是两批"要跑在 RISC-V 机器上"的程序——内核镜像
target/kernel，和一堆用户程序（_init、_sh、_ls 等）。不能用普通
gcc，是因为普通 gcc 只会把你的 C 代码翻译成 x86 的机器指令，而 xv6
要跑的那台是 RISC-V 机器，它只听得懂 RISC-V 的机器指令。

下面把这两个半句各说清楚。

先回答"编什么"。 看你 Makefile 第 108 行：

build: $T/kernel userprogs

build 这个目标依赖两个东西，所以它做两件事：

1. $T/kernel（第 102~106 行）：把 kernel/ 下的 .c 和 .S 文件编译、链接成一个
   ELF 内核镜像 target/kernel。OBJS 那一长串（第 16~58
   行）就是内核的源文件清单。
2. userprogs（第 214 行）：编译 xv6-user/ 下的
   init.c、sh.c、ls.c……生成带下划线前缀的用户程序
   _init、_sh、_ls，这些之后会被打包进 fs.img。

注意：这两批东西都不是给你这台电脑运行的，它们最终都装进 QEMU 模拟的那台
RISC-V 机器里。

再回答"为什么不能用普通 gcc"。 这里有个关键认知要建立：编译器本质是翻译器。C
语言机器不直接认识，编译器要把它翻译成 CPU
能直接执行的机器指令。而机器指令不是统一的——每种 CPU
架构有自己的一套"方言"，这就是指令集（ISA）：

- 你电脑的 CPU 是 x86_64 架构，只认 x86 机器指令；
- xv6 要跑的是 RISC-V 架构，只认 RISC-V 机器指令。

普通 gcc 装在你的 x86 电脑上，它默认就翻译成 x86 方言。拿它去编
xv6，编出来的东西那台 RISC-V 假机器一个字都听不懂。

所以要把编译器换成 riscv64-unknown-elf-gcc。看 Makefile 第 68 行：

TOOLPREFIX    := riscv64-unknown-elf-

这一行决定了后面 CC = $(TOOLPREFIX)gcc 到底调用哪个编译器。这个
riscv64-unknown-elf-gcc 的特别之处在于：它自己也运行在你的 x86
电脑上，但翻译出来的却是 RISC-V
机器指令——这正是"交叉编译"里"交叉"二字的含义：编译器和目标机器不是一个架构。

到这里先停一下。你现在可能想问：那我怎么知道它翻译出来的真的是 RISC-V
指令、而不是嘴上说说？——这可以引出一个小验证手段（用 file 命令看 target/kernel
的架构），等你想试时我们再继续。或者，你也可以先回到上一步，把之前那两条版本
确认命令跑了，确认你的机器上到底有没有这个交叉编译器。

### Turn 5

#### User

ls指令和ls /bin指令他们都干了什么，为什么有一部分输出是一样的

#### Claude

这问题问得很细，正好能把"文件系统里文件到底放在哪"这件事看清楚。

一句话回答： ls 列的是当前目录（也就是根目录 /），ls /bin 列的是 /bin
这个子目录；它们的输出有一部分一模一样，是因为 make fs
在生成镜像时，把每个用户程序在根目录和 /bin 各放了一份副本。

先拆成两小问。

第一小问：ls 和 ls /bin 各自在干什么。 关键线索就在提示符里：

-> / $

中间那个 / 就是当前工作目录——你现在站在根目录上。所以：

- ls 没带参数，就列当前目录（根目录 /）里的内容：你会看到
  init、sh、ls、cat、README，还有一个 bin 目录。
- ls /bin 是带了一个绝对路径参数，它去列 /bin
  目录里的内容，跟"你现在站在哪"无关。

这里有个隐藏概念值得点一下：ls 后面跟的是路径，/bin 是以 /
开头的绝对路径（从根目录一路指过去），所以它永远指同一个地方。

第二小问：为什么有一部分输出一样。 答案不在运行时，而在当初生成 fs.img
的时候。看你 Makefile 里 fs 这个 target（第 229~231 行）：

@for file in $$( ls $U/_* ); do \
    sudo cp $$file $(dst)/$${file#$U/_};\
    sudo cp $$file $(dst)/bin/$${file#$U/_}; done

这段循环对 xv6-user/ 下每一个 _
开头的程序（_init、_sh、_ls……）都做了两次拷贝：

1. 拷到镜像根目录 /，并且去掉下划线前缀 → 变成 /init、/sh、/ls；
2. 再拷一份到 /bin 目录 → 变成 /bin/init、/bin/sh、/bin/ls。

所以 / 和 /bin 里躺着同一批程序的两个副本，你 ls 和 ls /bin
自然就会看到重复的名字。这也是实验指导任务5里说的"拷进去的同时，建一个 bin/
子目录放一份副本"。

到这里先停一下。你可能会接着好奇：那为什么非要放两份？根目录有 init
不就够了吗？——这涉及内核是怎么找 init 的（它在根目录找），以及 bin/ 这个目录更
多是给用户一个"所有可执行程序集中放一处"的约定。想深挖哪个，我们可以继续。
